# 原生后端整改验收

日期：2026-10-12。基于 [Django 残留审计](django-residual-audit.md) 逐项整改；原审计保留整改前的事实。本报告对应工作区变更，线上部署不在本轮执行范围。

## 整改范围

| 原问题 | 处理结果 |
| --- | --- |
| 旧刷新令牌和撤销表名 | 新增 Alembic `0003_native_schema`，迁入 `cb_refresh_tokens`、`cb_revoked_tokens`，保留 ID、令牌及撤销状态 |
| 七张旧框架元数据表 | 行数据带来源归档至 `cb_migration_archive` 后移除原表；注销账号不再查询 `django_admin_log` |
| 新旧库约束和索引不一致 | 冻结 `schema_v3`，预检数据后构建统一结构；补齐唯一键、外键、UID/版本检查及选定查询索引；不修改已发布 `schema_v1` |
| 错误数据或扩展被误接管 | 在业务写入前检查缺表、列、类型、重复键、孤儿、空值、长度、非法 JSON/日期/UUID、扩展外键、触发器及视图；不通过删除业务行修复 |
| MySQL 迁移可能有损 | 长文本使用 LONGTEXT，排序使用 DOUBLE，时间使用 DATETIME(6)，目标字符集使用 utf8mb4；替换原表前流式比对规范化内容摘要，拒绝任何不一致 |
| UID 路径、排序、导入与数据库限制冲突 | 统一为 1–64 字符；缺失导入 UID 可生成，显式非法值按导入协议报告；保留 Unicode UID |
| 2001 个标签无法全量排序 | 移除列表静默截断，完整返回账号标签，并使用确定性排序 |
| OpenAPI 与实际响应不一致 | 补记录创建/幂等重放 201/200、标签创建 201、Cookie CSRF header 和公共业务错误响应 |
| 认证依赖形同虚设 | 服务使用依赖解析的 Bearer、Session 和 CSRF；保留显式空 Bearer 不回退 Cookie 的安全语义 |
| 死代码、重复校验、数据库错误混淆 | 删除失效校验；一般数据库故障使用 `database_unavailable`，确定约束失败使用 `database_conflict`；不确定提交保留重试协议；日志不输出 SQL 参数或凭据 |
| 旧部署配置和探活别名 | 移除 STATIC_ROOT/staticfiles、GUNICORN_WORKERS 别名和失效挂载；探活使用规范路径 |
| Nginx 媒体直读和遗漏后端入口 | 禁止 `/media/` 直接读盘；API、SQLAdmin、后台静态资源、公共页面、healthz 正确转发；保留 Host 端口及上游 HTTPS |
| 当前文档误称 Django 架构 | README、技术栈、能力规范、性能复现步骤统一到原生实现；历史设计和旧测量加历史标记，保留原事实 |
| 本地遗留文件 | 删除已核对的未跟踪旧 Django 临时脚本、临时依赖文件与 chewy_space 名称构建产物；保留用户记录和业务数据 |

## 兼容边界

运行依赖和请求处理不再使用 Django/DRF。旧 URL、查询参数别名、密码哈希格式、JWT claim、Cookie 名称、分页响应以及持久化 `post_tags` 草稿仍保留兼容，集中在原生实现中，并有回归覆盖。它们不要求安装旧框架。评论的资源路径本身符合 REST，也不是框架残留。

迁移脚本、旧库测试夹具和历史材料仍然含旧表名及 Django 字样，这是升级和追溯所需。业务 `cb_*` 表、仍有实际用途的权限字段和附件字符串标识不做无意义改名。旧索引按当前查询选择并统一命名，不恢复重复索引；新旧库都采用当前原生 ID 语义，不承诺已删除最高 ID 永不复用。
