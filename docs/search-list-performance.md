# 搜索、筛选与列表性能

Web 列表显示关键词、标签、开始/结束日期和附件条件，可逐项移除或全部清除。移动端入口统一称为“筛选”，关闭面板后条件仍在列表上方；“首页”清空全部条件。正文的搜索高亮按文字匹配，保留链接地址、代码内容与 Markdown 安全清理。跨 Markdown 节点的完整短语不保证连续高亮。

## 复现方法

在 backend 目录执行：

```sh
uv run python benchmark_feed.py --sizes 1000 10000 --repeats 10
```

脚本强制创建临时 SQLite、运行迁移并在结束时清理，不接受现有数据库地址。每个账号分别有 1,000 / 10,000 条约 350 字符的记录，每条关联三个标签和三条评论，10% 正文命中关键词，所有记录命中标签词。两组账号共存于同一临时数据库。每页 100 条，测试首屏、最后一页、正文关键词、标签关键词与精确标签筛选。

使用真实 DRF APIClient、视图、过滤器、序列化及 JSON 渲染，认证使用测试工具注入账号，不包含 JWT 解析、网络、Nginx、图片下载或浏览器布局。记录查询数、返回条数与字节数，并断言评论数和记录去重正确。

`before` 固定复现 80bce0f 的 queryset 与标签过滤方式；`after` 调用当前实现。每组先预热，每轮交替执行两个版本，并交替交换先后顺序。p50 为中位数；10 次采样的 p95 采用最近秩法，实际对应最大值。SQL 时间仅统计 execute 耗时，不包含全部取行与序列化开销。

## 查询调整

原列表先将整组记录与评论连接并分组，再执行分页总数和排序。改为相关子查询计算评论数，让分页总数无需为每条记录聚合评论；精确标签过滤采用 EXISTS，避免引入重复行。排序增加主键作为相同更新时间的次级依据，不改变置顶优先规则。无需数据库迁移或新增依赖。

`test_feed_queries.py` 覆盖多标签命中时评论数不膨胀、零评论、账号隔离、相同时间下跨页无重复，以及每页恒定三次查询。

## 适用范围

结果只代表报告所列本机环境与合成数据，不能外推为生产容量承诺。未进行并发压力、超长正文、媒体加载、持续滚动至数千张卡片或其他数据库引擎的性能验收；后续根据真实使用规模测量，必要时再考虑索引、全文检索和列表虚拟化。

## 2026-09-07 对照结果

环境：Windows 11、Python 3.14.4、Django 6.0、临时 SQLite；每组预热后 10 次交替采样。原始数据见 [feed-benchmark-comparison.json](feed-benchmark-comparison.json)。早期分开运行时受本机负载影响较大，下表采用配对测量；不把所有 p95 波动解释为代码收益。

| 记录量 | 场景 | 原 p50 / p95（ms） | 新 p50 / p95（ms） |
|---:|---|---:|---:|
| 1,000 | 首屏 | 29.48 / 37.64 | 24.34 / 36.85 |
| 1,000 | 末页 | 31.31 / 43.08 | 25.28 / 52.91 |
| 1,000 | 正文搜索 | 37.94 / 46.03 | 28.81 / 31.49 |
| 1,000 | 标签关键词 | 48.24 / 52.03 | 28.67 / 60.27 |
| 1,000 | 精确标签 | 34.19 / 36.79 | 28.15 / 33.53 |
| 10,000 | 首屏 | 127.70 / 139.74 | 49.82 / 97.12 |
| 10,000 | 末页 | 150.94 / 170.97 | 70.72 / 83.68 |
| 10,000 | 正文搜索 | 177.71 / 192.30 | 77.67 / 119.23 |
| 10,000 | 标签关键词 | 293.61 / 317.59 | 74.00 / 120.80 |
| 10,000 | 精确标签 | 145.30 / 159.34 | 67.99 / 101.82 |

所有场景均返回 100 条、执行 3 次查询。1 万条记录首屏 p50 约下降 61%，标签关键词约下降 75%；千条数据的个别 p95 反而升高，因此不能宣称所有请求尾延迟都改善。没有引入全文检索或虚拟列表。
