## Context

Web 列表采用服务端筛选和分页，默认每页 100 条。当前查询关联标签及评论计数，搜索通过 DRF SearchFilter 完成；尚未量化深分页与标签搜索成本。

## Goals / Non-Goals

目标：筛选状态清晰可撤销，Markdown 搜索命中可见，性能测量可复现且结果正确。
非目标：全文搜索服务、重构编辑入口、移动端原生改版、生产数据库压测。

## Decisions

### 方案选型

- 复用现有筛选 state/API，在列表上方呈现条件按钮；每个按钮只移除自身，全部清除包含标签。桌面与移动弹窗共用清除函数；空结果按全部条件判断。
- 在 sanitize 之后遍历 Markdown 文本节点，生成固定 mark 元素。输入只作为转义后的文字匹配，不作为 HTML 或正则表达式执行；链接地址和代码内容结构保留。匹配词按空白、逗号及引号短语解析，与现有搜索惯例一致。
- 临时 SQLite 中构造 1,000 和 10,000 条记录、标签与评论，用真实 DRF 响应测量首屏、深分页、关键词与标签搜索，保存 p50/p95、返回条数、查询数和环境。仅在发现瓶颈后修改查询，保留优化前后证据。

### 未采纳方案及原因

- 字符串替换 HTML：容易破坏 Markdown 或引入注入；采用结构化文本节点。
- 直接引入全文索引/虚拟列表：尚无测量依据，会扩大部署和交互复杂度。
- 在线压测：可能干扰用户数据和服务；独立临时数据可复现。

## Risks / Trade-offs

- 跨 Markdown 节点的短语可能无法连续高亮 → 保留原内容，不假造匹配，验证常规正文、链接和代码。
- 本机结果不能代表部署容量 → 报告标注环境、数据分布与缺少网络/并发负载的限制。
- 查询优化影响计数和权限 → 加入多标签、多评论、账号隔离及稳定分页回归。

## Migration Plan

完成局部与全量检查后提交推送，跟进 CI 与镜像部署；默认不变更数据结构，若测量需要索引则追加明确迁移与验证。
