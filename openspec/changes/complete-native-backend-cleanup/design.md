## Context

以 docs/django-residual-audit.md 为已确认问题清单。用户已要求全部修复；采用数据库、接口、文档部署三条独立工作线。业务 ID、密码、令牌、存储密钥和附件路径必须保留，初始迁移冻结不改。

## Goals / Non-Goals

目标是移除当前运行结构对旧框架表名的依赖、统一新旧库的关键结构、修复已复现问题，完成契约、部署、文档和测试。历史 fixture 与明确标注的历史报告继续保留；不将通用 REST、snake_case、Session 或业务 cb_* 命名视为错误。不发布线上部署、不重置账号。

## Decisions

- 令牌表使用 `cb_refresh_tokens` / `cb_revoked_tokens`；旧表的数据、主键、撤销关系保留。旧框架表非空数据先保存到独立原生归档表 `cb_migration_archive`（来源、序列、可还原行内容），再移除旧表；空库也具有一致归档表结构。相比直接 DROP，归档避免丢失旧管理日志；相比改名七张无用表，单一归档不保留框架运行结构。
- 新增冻结目标 schema 与 revision，UID 列长度为 64。迁移前验证结构/值，遇重复唯一键、孤儿或超长 UID 拒绝且不改业务数据；缺失约束且数据有效则修复。按当前查询补必要联合索引和规范名称；对已有版本复跑不重复归档或复制。
- 标签 GET 保持数组协议并返回完整集合、确定性排序，使现有三端全量排序可继续工作；不引入客户端尚未支持的分页响应。UID 共享 Pydantic 类型与导入校验，非法值不能产生无法读取的记录。
- 认证使用 FastAPI 已解析的凭据与 CSRF Header；认证服务不重读 HTTP Request。共享配置/限流依赖按必要范围封装，不为风格重写业务函数。
- OpenAPI 显式包含动态成功状态和错误；数据库错误用通用代码分类，日志仅记录安全元信息，不输出 SQL 参数、密码或令牌。
- URL/旧载荷/密码/JWT 兼容是已发布协议，集中到兼容边界并明确说明；删除会破坏旧附件链接和离线待提交记录，因此本次不取消这些协议。
- 清除无消费者的 STATIC_ROOT/staticfiles 配置、旧 worker 别名及失效临时文件；更新当前说明，对历史材料加醒目标记，不篡改原测试环境。

## Risks / Trade-offs

- 复制不能只检查行数 → 替换原表前流式核对规范化内容 SHA-256；MySQL 使用 utf8mb4、LONGTEXT、DOUBLE、DATETIME(6)，非严格 SQL 模式也必须保留业务值。
- 未知数据库扩展可能被重建破坏 → 自定义视图、触发器、额外唯一/CHECK 约束或扩展外键明确拒绝，先单独迁移扩展规则。

- 大库重建/加约束需要停写窗口 → 先在备份副本验证，迁移前检查并提供可恢复备份。
- SQLite、PostgreSQL、MySQL DDL 不同 → 使用方言合适的迁移方式，真实可用数据库做集成验证，无法运行的后端在报告中注明。
- 异常旧数据不能静默丢弃 → 明确拒绝并给出表/约束名称，不打印业务值。
- 完整标签数组可能很大 → 保持已有操作正确性，后续分页需三端协议一起设计；本次不继续静默截断。

## Migration Plan

实现并通过空库、合成旧库、已接管旧库、缺约束、重复/孤儿、长 UID、令牌轮换等测试。对本地数据库先做 SQLite backup 并只读校验，副本升级和逻辑内容比对通过后再处理实际运行库；检测仍在运行的旧服务时先不原地替换。线上由维护者按文档停旧服务、备份、执行 CLI migrate、启动新程序；回退恢复完整数据库与旧代码。

## Open Questions

无阻塞需求问题。远端数据库服务可用性在验收时核实；不把编译检查冒充跨数据库实测。
