## Context

当前镜像发布到 ghcr.io/cone387/chewy-bbtalk，部署却执行 update cn。服务器有 Docker 兼容命令（日志显示实际构建使用 Podman），故使用通用容器 CLI 操作，避免 Docker 专属 Compose 依赖。

## Goals / Non-Goals

目标：部署同一构建产物、拉取失败不影响旧服务、检查后才报告成功。非目标：零停机、数据库自动回滚、运行时注入 Vite 配置或更换镜像仓库。

## Decisions

### 方案选型

- build job 输出镜像 digest；部署串行且不取消正在执行的切换。远端检查 master 最新提交，过期构建跳过；从指定提交读取部署脚本而不覆盖工作区文件。
- 专用脚本使用工作目录 .env 和 data、4010 端口。持有 flock，拉取失败有限重试，拉取/预检成功前不停止容器。
- 旧容器停机后改名为 chewy-bbtalk-previous；新容器健康后删除旧容器。启动/健康失败保留旧容器和新容器现场，非零退出，禁止自动回滚数据库。检测残留 previous 或双旧名称时在切换前停止并提示人工处理。
- 健康检查通过容器内 Python 检查 Nginx 首页和 Django 用户 API 的预期状态及 JSON 响应；不打印容器环境或可能含密钥的应用日志。
- 用 mock 容器 CLI 执行真实 Bash 脚本覆盖拉取、启动、检查失败等分支；真实镜像运行仍以远端流水线为准。

### 未采纳方案及原因

- 增加 Git 下载重试但继续重建：没有消除重复依赖拉取与产物不一致。
- 部署 latest：可能取到另一提交。
- 自动启动旧容器：迁移可能已改变数据库，不能承诺安全回滚。

## Risks / Trade-offs

GHCR 在服务器不可达时部署仍会失败，但旧服务保持运行。预构建镜像使用构建时 Web 配置；服务端 .env 仅提供运行时后端配置。容器切换有短暂中断，失败迁移需人工检查与备份恢复。flock 为 Linux util-linux 工具，缺失则在切换前失败。
