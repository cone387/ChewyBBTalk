## Context

三端共用 DRF API，现有 POST 无幂等键，编辑无服务端版本条件。Web 草稿使用 IndexedDB，原生使用本地持久存储，桌面通过主进程 API。前台刷新需保护会话、筛选和正在编辑的内容。Web 使用 Chromium 回归；初始化含固定默认密码。

## Goals / Non-Goals

目标：完成用户批准的三项改进，并验证三端提交行为、跨浏览器关键流程及部署兼容。
非目标：PWA、自动离线发布、WebSocket、真机验收、阅读编辑入口重构、自动更换现有管理员凭据。

## Decisions

### 方案选型

- 新客户端创建记录携带 Idempotency-Key。服务端以用户+键唯一约束建立持久提交回执，与记录和标签在同一数据库事务内提交。相同键相同载荷返回同一记录；不同载荷返回 409；已删除记录返回 410，不复活。提供账号内结果查询，旧客户端无键仍可发布。回执不自动过期，避免长时间离线重试产生重复。
- 三端在首次请求前持久保存键和原始提交载荷，响应不确定时核对或重试原提交；确认完成后清理。按服务器、用户和编辑目标隔离，写入失败明确阻止无法保障恢复的提交。用户修改未确认内容时需先处理原提交，不能悄悄生成新键。
- 编辑使用现有 update_time 作为版本标识，通过 If-Match 条件和事务锁比较。冲突返回 409 并保留输入，用户可核对最新记录后决定。未带条件的旧客户端兼容，但不承诺其冲突保护。
- Web visibility/focus/online、原生 AppState 恢复时刷新，节流并拒绝旧会话/旧筛选响应；刷新不覆盖编辑器内容。桌面没有 feed，处理唤醒后的会话核对、持久提交及成功状态。
- 统一 Web 确认和错误反馈，危险操作等待明确确认，错误保留操作上下文。跨浏览器验证登录、发布、重试、编辑冲突、筛选和基本键盘交互。
- 新安装使用显式管理员密码或生成随机初始化密码并仅保存到受限文件；不覆盖已有账号。注册可配置，默认关闭；登录/注册限流可配置并提供明确 429 反馈。状态入口区分普通用户的自身存储/备份状态与管理员服务诊断，避免泄漏密钥、路径和其他用户信息。

### 未采纳方案及原因

- 只禁用发布按钮：不能处理响应丢失、重启和重复请求。
- 自动更换重试键：会绕过去重，必须保存提交身份。
- 仅前端比较版本：无法阻止并发写入覆盖。
- 全站实时推送/自动离线补发：成本高且可能产生用户未确认发布，先完成前台刷新和明确重试。

## Risks / Trade-offs

- SQLite 并发写冲突 → 返回可重试错误，重试沿用同一键；数据库唯一约束是最终保护。
- 回执长期保留增加存储 → 只存请求摘要、关联记录和键，不复制正文/附件。
- 浏览器恢复环境差异 → Linux CI 验证 WebKit/Firefox，本地可用引擎验证布局；不声称代替真机。
- 应用限流受缓存后端影响 → 记录多进程边界，生产可使用共享缓存/反向代理进一步限制。

## Migration Plan

先部署兼容的后端回执表与版本协议，再接入三端；保留旧请求契约。初始化配置变更更新 README、示例配置与隔离测试环境。每轮完成自动检查、提交推送和部署检查，最终按全部任务验收。
